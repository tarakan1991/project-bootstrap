# Bootstrap документации нового проекта

Скилл — **опросник**. Он не пишет документацию из головы: задаёт вопросы, по ответам собирает каркас из готовых шаблонов, а всё, на что ответа нет, оформляет **триггером** («появится X → создать/заполнить Y») — не пустым файлом и не выдумкой.

Константы конституции (переносятся всегда, не спрашиваются):

- задачи в трекере, не в markdown; ADR для нетривиальных решений; «один факт — один дом» + каскадное обновление;
- **архитектура, стек и хранилище — не пункты анкеты**: они либо уже приняты (тогда фиксируются), либо выбираются осознанно — варианты с trade-offs, решение за человеком, фиксация ADR, — либо откладываются в триггер. Скилл никогда не выбирает их за пользователя и не принимает ответ «на бегу»;
- `AGENTS.md` = бюджет инструкций: корневой роутер + модульные по триггеру; `CLAUDE.md` = стаб `@AGENTS.md`;
- секреты в репо нельзя; reference (API-контракты, env) генерируется из кода, не пишется руками;
- docs-only изменения не гоняют CI;
- исходим из того, что над проектом работают несколько человек и несколько ИИ-агентов, даже если сегодня участник один.

Шаблоны — в `templates/` рядом с этим SKILL.md; дерево зеркалит корень целевого репо. Формулировки в шаблонах обкатаны — не пересочинять без причины.

## Режим 1 — бутстрап (каркаса ещё нет)

### Шаг 0 — предусловия

1. Работай в корне нового проекта. Не git-репозиторий → предложи `git init`.
2. Уже есть `AGENTS.md` / `CLAUDE.md` / непустой `docs/` → это режим 2 (дозаполнение); если сомневаешься — спроси. Существующий `README.md` не перезаписывать, а дополнять.
3. **Определи хостинг** по `git remote -v`: `github.com` → GitHub; `gitlab` в хосте (включая self-hosted вроде `gitlab.company.ru`) → GitLab; другое или remote нет → спросишь в волне 2. Определившееся подтверди у пользователя одной строкой — от хостинга зависят пути шаблонов, CI-файл, защита ветки и терминология PR/MR.

### Шаг 1 — волна 1: продукт (свободные вопросы, задавать в чате списком)

1. **Что за проект.** Название + 2–3 предложения: какую проблему решает, для кого.
2. **Пользователи и сценарии.** Кто пользователи (роли)? 2–5 главных сценариев «приходит → делает → получает»? Известные бизнес-правила («как считается X», «когда наступает Y»)?
3. **Участники.** Люди + роли (owner, разработчики, менеджеры); какие ИИ-агенты работают (Claude Code, Codex, …).

Правило волны: **«пока не знаю» — валидный ответ на всё**. Он превращается в строку таблицы триггеров, а не в выдуманный текст.

### Шаг 1.5 — архитектура: осознанный выбор, не анкета

Про форму, стек и данные НЕ спрашивать анкетой. Задай один вопрос-развилку: **«Архитектурные решения — форма (веб-сервис/бот/CLI/…), крупные части, стек, хранилище — уже приняты, или будем выбирать?»**

- **Уже приняты** → зафиксируй как данность (это уточнение принятых решений, не выбор): что проект физически; крупные части (фронт, бэк, БД, фоновые задачи); HTTP API / UI; стек; хранилище, миграции, как ИИ-агент будет читать актуальную схему (модели в коде / миграции / генерируемый дамп). Нетривиальные решения без записанного «почему» → предложи оформить ADR задним числом.
- **Не приняты (или частично)** → не вписывай первое сказанное и не выбирай сам. Предложи пользователю два пути:
  - **выбрать сейчас, осознанно:** предложи 2–3 варианта под проект из ответов волны 1, каждый с плюсами/минусами по внятным осям (простота, скорость до результата, деплой, опыт участников). Решение принимает пользователь. Принятое зафиксируй как ADR (см. шаг 3);
  - **отложить:** строка в таблицу триггеров — «выбран стек/хранилище → провести осознанный выбор (варианты + ADR), создать дома architecture/».
- Частично принятые решения комбинируй: принятое фиксируй, непринятое — по развилке выше.

**Ответ пользователя «да пиши что-нибудь / выбери сам» — не принимать.** Вежливо объясни: это решение переживёт проект дольше любого кода, и предложи короткий выбор из 2–3 вариантов — либо триггер.

### Шаг 2 — волна 2: воркфлоу (вопросы с вариантами ответов; если инструмент поддерживает кнопочный выбор — например AskUserQuestion в Claude Code — использовать его, иначе задать списком в чате с пронумерованными вариантами)

1. **Git-режим:** `соло-лайт` (мелочь в main, крупное через PR) / `стандарт` (PR-only, самомерж по зелёному CI) / `команда` (PR-only + обязательное ревью). Выбор тянет **пресет воркфлоу задач** (таблица ниже) — покажи пресет одним экраном и спроси «что поправить?».
2. **Трекер:** пока нигде / ссылка на систему (любую). Если ссылка → есть ли API и ключ? Ключ НЕ в репо и НЕ в доки: env-переменная или MCP-конфиг; в `project-workflow.md` — только ссылка на систему и имя переменной.
3. **Прод и деплой:** прода пока нет / деплой руками / мерж в `main` = автодеплой на прод.
4. **CI:** пока нет / сразу.
5. **Тестовая политика:** `строго` (новая логика не мержится без тестов) / `прагматично` (тесты обязательны для критичной бизнес-логики) / `отложено` (прототипируем без тестов; триггер пересмотра — первый прод). **Предохранитель:** «автодеплой» + «отложено» → предупреди, что каждый мерж едет на прод без сетки, и порекомендуй минимум «прагматично».
6. **Хостинг репозитория** — только если не определился в шаге 0: GitHub / GitLab / другой / пока не решён. «Другой/не решён» → hosting-артефакты (шаблон PR/MR, CI-файл, раздел «Защита ветки») не создаются, уходят строкой в триггеры.

Объяви дефолт без вопроса: **язык коммитов и доков — русский** (возражение → поменять всюду).

#### Пресеты воркфлоу задач (по git-режиму)

| Пункт | Соло-лайт | Стандарт | Команда |
|---|---|---|---|
| Старт работы | крупное — с задачей, мелочь без | нет задачи — нет работы (искл. docs/chore) | нет задачи — нет работы (искл. docs/chore) |
| Задача при PR | упомянуть в описании | упомянуть + перевести «в работу/на проверку» | упомянуть + перевести |
| Отчёт в задаче | желателен | обязателен, по шаблону | обязателен, по шаблону |
| Закрывает задачу | автор после мержа | автор после проверки (при автодеплое — на проде) | постановщик после проверки |

| `docs/workflow/git-workflow.solo.md` / `.standard.md` / `.team.md` | `docs/workflow/git-workflow.md` | ровно один, по вопросу «git-режим» |

| `docs/workflow/agents.md` | туда же | всегда |

Правила заполнения:

- **`{{...}}`** → ответы интервью. После генерации `git grep -F '{{' -- '*.md'` должен вернуть пусто.
- **`<!-- ВАРИАНТ ... -->`** → оставить содержимое выбранного варианта, второй и маркеры удалить.
- **Ответа нет** → НЕ файл-пустышка и НЕ выдуманный текст, а строка в таблице «Дома по триггеру» в `docs/README.md`.
- **Хостинг GitLab** → в сгенерированных доках заменить терминологию: «PR» → «MR», «pull request» → «merge request»; кнопка «Create a branch» на issue → «Create merge request» (она тоже создаёт ветку); в `git-workflow.md` оставить GitLab-вариант раздела «Защита ветки» (GitHub-вариант с `gh api` удалить). GitHub — наоборот.
- Язык — русский. Секретов в доках нет. AGENTS.md не раздувать: тест строки — «уберу — агент начнёт ошибаться? Нет → режу».

### Шаг 4 — гигиена репозитория

1. `.gitignore` — дописать (если ещё нет): `logs/`, `scratch/*`, `!scratch/.gitkeep`, `CLAUDE.local.md`, `.env`.
2. Создать пустой `scratch/.gitkeep`.

### Шаг 5 — финал

1. Самопроверка: `{{` не осталось; варианты вырезаны; карты в `AGENTS.md` и `docs/README.md` = реально созданные файлы; таблица триггеров согласована с ответами.
2. Отчёт пользователю: список файлов + принятые решения (архитектура/стек: приняты / выбраны с ADR / отложены в триггер; git-режим, трекер, деплой, CI, тест-политика, правки пресета).
3. Первый коммит: `docs: разворачивает каркас документации проекта`. В пустом репо — прямо в `main` (для «стандарт»/«команда» это единственное допустимое исключение из PR-only; дальше действует регламент).
4. Следующие шаги вне репо (перечислить, самому без запроса не делать): настройки репозитория и защита ветки — по разделу «Защита ветки» в `git-workflow.md` (GitHub: squash-only + ruleset, нужен платный план для приватного репо; GitLab: squash=require, «Pipelines must succeed», protected branches — бесплатно, включать сразу); положить ключ трекера в env/MCP.

## Режим 2 — дозаполнение (каркас уже есть)

1. Прочитай `AGENTS.md` и `docs/README.md` — прежде всего таблицу «Дома по триггеру».
2. Сравни триггеры с реальностью репо: появился код? модули без `<модуль>/AGENTS.md`? прод/деплой-конфиги? HTTP-endpoints? UI? БД/миграции? Для каждого сработавшего триггера — предложи создать дом по формату из таблицы.
3. **Триггер «выбран стек/хранилище» закрывается только через осознанный выбор** (шаг 1.5 режима 1: варианты → решение пользователя → ADR), не через «впиши что стоит в package.json». Исключение: в репо уже есть код на конкретном стеке — тогда стек де-факто выбран, зафиксируй и предложи ADR задним числом.
4. Собери недозаполненное: `git grep -nE 'TODO|\{\{' -- '*.md'` по `docs/` и корневым файлам.
5. Опроси пользователя **только** по найденному (сработавшие триггеры + TODO) — полный опрос заново не гонять.
6. Заполни; сработавшие строки перенеси из «Домов по триггеру» в «Состав docs/»; прогони каскадную проверку ссылок (`workflow/agents.md`).

## Режим 3 — учебный (для курса)

Триггер: «bootstrap в учебном режиме» / «учебный бутстрап проекта».

Отличия от режима 1 (всё остальное — как в режиме 1, шаги 0, 3–5 без изменений):

- **Волна 1 — полностью** (что за проект, пользователи и сценарии, участники). «Пока не знаю» — валидный ответ, превращается в триггер.
- **Шаг 1.5 — всегда ветка «отложить»:** развилку не задавать, выбор сейчас не проводить. Архитектура/стек/данные уходят в триггеры; сам выбор — отдельное упражнение курса после бутстрапа (маршрут — в отчёте ниже).
- **Волну 2 НЕ задавать.** Применить учебный пресет без вопросов:
  - git-режим = `соло-лайт`;
  - трекер = пока нигде;
  - прод и деплой = прода пока нет;
  - CI = пока нет;
  - тестовая политика = `отложено`;
  - хостинг = <!-- УЧЕБНЫЙ ХОСТИНГ: вписать GitHub или GitLab после решения по курсу -->.
- **В отчёте (шаг 5.2) добавить отдельный блок** — дословно или близко к тексту:

  > Решения по воркфлоу приняты учебным пресетом курса — вы к каждому вернётесь на своём модуле:
  > трекер задач — модуль 2; тесты и CI — модули 3–4; прод и автодеплой — модуль 7.
  >
  > Архитектура, стек и хранилище данных намеренно НЕ выбраны — это ваше первое осознанное
  > инженерное решение. Следующий шаг: попросите агента предложить 2–3 варианта стека под ваш
  > проект с плюсами и минусами, примите решение сами, зафиксируйте его как ADR — и скажите
  > «дозаполни каркас»: сработают триггеры, появятся дома architecture/.
  >
  > Ваша таблица «Дома по триггеру» в docs/README.md — это карта курса в вашем репозитории: загляните в неё.

- **После отчёта показать пользователю таблицу «Дома по триггеру»** из сгенерированного `docs/README.md` и назвать её картой курса.
- Учебный режим не помечает репозиторий как «учебный» — каркас полноценный, дальше проект живёт по обычным режимам 1–2.
