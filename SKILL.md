# Bootstrap проекта

Скил ведёт интервью и по ответам собирает каркас из готовых шаблонов. Он **не пишет документацию из головы**: то, на что ответа нет, становится строкой в таблице «Дома по триггеру» — «появится X → создать Y», — а не пустым файлом и не выдумкой.

Шаблоны — в `templates/` рядом с этим файлом, дерево зеркалит корень целевого репозитория. Развёрнутые тексты, которые предъявляются человеку, — в `reference/`. Формулировки обкатаны, **не пересочинять**.

## Как говорить с человеком

Перед первым вопросом прочитать `reference/axes.md`, `reference/strategies.md`, `reference/commits.md` и `reference/review-process.md` и предъявлять варианты **оттуда**, дословно.

1. **Шаблон варианта: что происходит и что даёт → цена → когда подходит.** Три части, в этом порядке. Вариант без цены — человек не понимает, что выбирает, и отвечает наугад.
2. **Термин вводится при первом появлении.** «Ветка — отдельная копия кода», «pull request — страница с твоими изменениями».
3. **Жаргон переводится.** Не «хостинг», а «где лежит репозиторий»; не «автодеплой», а «автоматический выкат»; не «squash», а «схлопнуть в один коммит»; не «rebase», а «перенести свои коммиты поверх свежей ветки»; не «покрытие», а «какая часть кода затрагивается тестами».
4. **Скил не спорит с выбором.** Цена показывается **до** выбора и только для вариантов из списка. Человек выбрал или назвал своё — дальше уточняющие вопросы и генерация, без «устарело» и «сейчас так не делают».
5. **«Не знаю» — валидный ответ.** Берётся предложенный вариант с обоснованием, в триггеры уходит строка на пересмотр. Исключение — архитектура: «реши за меня» не принимается (см. вход A).
6. **Ничего не блокирует бутстрап.** Отказ, отсутствующий инструмент, нерешённое место репозитория — всё это строки в триггеры, а не остановка.

## Константы — переносятся всегда, не обсуждаются

- **ADR для нетривиальных решений**: решение с последствиями фиксируется вместе с «почему», append-only.
- **Один факт — один дом + каскадное обновление**: факт живёт в одном месте, остальные ссылаются; правка факта обновляет все его места в одном изменении.
- **Тест — контракт, а не препятствие**: падает тест — чинится код. Менять или удалять тест ради того, чтобы проверка прошла, нельзя — это отдельное решение человека с объяснением, почему прежнее ожидание было неверным. Ослабить утверждение, подменить проверяемое поведение заглушкой, пометить тест пропускаемым — то же самое, что удалить проверку. Кладётся всегда, даже когда тестов ещё нет.
- **Разрушающее изменение схемы данных не едет вместе с тем изменением, которое его вводит**: сначала аддитивная часть, разрушающая — отдельным шагом позже. Причина называется прямо: откат кода не откатывает данные. Перед операцией, способной потерять данные, — резервная копия задетых таблиц.

  Константы про тесты и про миграции формулируются нейтрально — «чтобы проверка прошла», «изменение», а не «зелёный CI» и «выкат»: они кладутся в любой конфигурации, в том числе там, где ни проверок, ни прода ещё нет. Файлы, которые они называют (`env.example`, `CLAUDE.local.md`), тоже упоминаются всегда: это указание на дом, а не ссылка на существующий документ.
- **Секреты в репозитории не хранятся**: переменные объявляются в `env.example` без значений; ключи — в окружении или конфиге инструмента.
- Задачи не ведутся в markdown репозитория.

## Шаг 0 — где лежит репозиторий

От этого зависят: название предложения изменений (pull request на GitHub / merge request на GitLab), пути шаблонов и настроек проверок, механика защиты главной ветки. Подробности — `reference/hosting.md`.

1. Не git-репозиторий → предложить `git init`.
2. `git remote -v`:
   - **remote есть** → определить место по хосту: `github.com` → GitHub; `gitlab` в хосте, включая свой сервер → GitLab; иначе «другое». Подтвердить одной строкой, идти дальше.
   - **remote нет** → спросить: «Репозиторий уже где-то заведён?»
3. **Дали ссылку** → определить место по хосту → `git remote add origin <url>` → проверить `git ls-remote --exit-code origin`. Недоступен — сказать, что именно не сработало, предложить исправить ссылку, настроить доступ или продолжить без remote.
4. **Репозитория нет** → «Где заводим: GitHub · GitLab · пока не решили». «Пока не решили» — валидный ответ: артефакты места уходят строкой в триггеры.
5. **Выбрали GitHub/GitLab** → проверить готовность инструмента: `gh --version` / `glab --version`, затем `gh auth status` / `glab auth status`.
   - не установлен → показать команду (`winget install --id GitHub.cli` · `brew install gh`; `winget install --id glab.glab` · `brew install glab`) и **спросить разрешение**. На Windows после установки проверять версию в новом окне терминала — установщик правит `PATH`.
   - не авторизован → отдать человеку команду `gh auth login` (`glab auth login`) и ждать. **Интерактивный вход агент у себя не запускает** — он повиснет. Токен текстом в чате не принимается и в файлы не пишется.
   - отказ ставить → ручной путь: короткая инструкция создать репозиторий в веб-интерфейсе и вернуть ссылку; либо «позже» — тогда первый коммит останется локальным.
6. **Публичный или закрытый.** Спросить прямо, а не выводить по косвенным признакам: от этого зависит раздел про вклад со стороны, язык коммитов и оговорка про платный план в защите ветки. Репозиторий уже существует → определить по факту и подтвердить одной строкой.
7. **Создание — на шаге 7**, не сейчас: до генерации пушить нечего.

| Признак | Вход |

Сомневаешься — спроси. Существующий `README.md` не перезаписывается, а дополняется.

## Вход A — пустой проект

### A1. Продукт (свободные вопросы, списком)

1. **Как называется проект.** Отдельный вопрос, не часть описания: название идёт в заголовки четырёх файлов. Названия ещё нет → взять рабочее из каталога или адреса репозитория и **сказать, что оно рабочее**, а не молча подставить.
2. **Что за проект.** 2–3 предложения: какую проблему решает, для кого.
3. **Пользователи и сценарии.** Кто пользователи? 2–5 сценариев «приходит → делает → получает»? Известные правила предметной области?
4. **Участники.** Сколько людей пишет код, их имена и роли; какие ИИ-агенты работают. Имена не назвали — записать числом («трое разработчиков»), не выдумывать.

«Пока не знаю» → строка в триггеры либо пометка внутри файла (см. ниже), не выдуманный текст.

**Кто считается участником.** В предохранителях «участников больше одного» считаются **люди**, пишущие код. ИИ-агент участником не считается: он работает от имени человека и не создаёт второго независимого источника изменений. Но если агенты работают в репозитории постоянно, это стоит сказать вслух при `strategy=trunk`: изменений в общей ветке будет больше, чем людей.

### A2. Архитектура — разговором, не анкетой

Не спрашивать таблицей про форму, стек и хранилище. Задать развилку: **«Архитектурные решения — форма (веб-сервис, бот, CLI…), крупные части, стек, хранилище — уже приняты или будем выбирать?»**

- **Приняты** → зафиксировать как данность: что проект физически, из каких частей состоит, какой стек, где данные, как агент узнаёт актуальную схему. Решения без записанного «почему» → предложить ADR задним числом.
- **Не приняты** → собрать вводные (что за продукт из A1, опыт участников, сроки, ограничения), предложить 2–3 варианта с плюсами и минусами по внятным осям, решение принимает человек, результат — ADR.
- **Откладываем** → строка в триггеры: «выбран стек/хранилище → провести осознанный выбор, создать дома architecture/».

**«Выбери сам» не принимается.** Объяснить: это решение переживёт проект дольше любого кода. Предложить короткий выбор или откладывание.

### A3. Дальше — шаги 2–7.

## Вход B — существующий проект

Стек, структура и сложившийся процесс **вычитываются**, а не выспрашиваются.

| Что смотреть | Где |
|---|---|
| Стек и зависимости | манифесты пакетов |
| Структура | дерево каталогов, точки входа |
| Хранилище и схема | модели, каталог миграций |
| Проверки | настройки автоматических проверок, конфиги линтеров, наличие тестов |
| Выкат | job выката: сам на вливание → автоматический; ручной запуск → по кнопке; только конфиги → руками |
| Стратегия ветвления | `git branch -r`: постоянные `develop`/`staging`/`production` → ветки окружений; `release/*`+`hotfix/*` → назвать то, что видно, и уточнить |
| Как вливают | `git log --merges`: есть коммиты слияния → не схлопывают; линейная история → схлопывают |
| Имена веток и формат коммитов | `git branch -r`, последние ~50 сообщений |
| Участники | `git log --format=%ae` за последние ~100 коммитов |
| Порог покрытия | настройки прогона тестов — если задан, зафиксировать как есть, не возражать |

Показать **одной сводкой**: «вижу вот это → предлагаю такой набор. Что поправить?». После подтверждения спросить только то, чего в репозитории не видно: продукт и пользователи (A1), недостающие оси.

Нетривиальные решения без записанного «почему» → предложить ADR задним числом.

## Вход C — дозаполнение

1. Прочитать `AGENTS.md` и `docs/README.md`, прежде всего таблицу «Дома по триггеру».
2. Сверить триггеры с реальностью: появился код? модули без `<модуль>/AGENTS.md`? прод? HTTP-endpoints? UI? база и миграции? Для каждого сработавшего — предложить создать дом.
3. Триггер «выбран стек/хранилище» закрывается только осознанным выбором (A2). Исключение: код уже написан на конкретном стеке — зафиксировать по факту и предложить ADR задним числом.
4. Собрать недозаполненное: `git grep -nE 'TODO|\{\{' -- '*.md'`.
5. Спросить **только** по найденному. Полный опрос заново не гонять.
6. Заполнить, перенести сработавшие строки из «Домов по триггеру» в «Состав docs/», прогнать каскадную проверку (`workflow/agents.md`).

## Шаг 2 — стратегия ветвления

Тексты вариантов — `reference/strategies.md`, предъявлять дословно.

| Идентификатор | Коротко |
|---|---|
| `trunk` | все пишут сразу в общую ветку |
| `branch-per-task` | каждая задача — отдельная ветка, вливается через запрос на слияние |
| `env-branches` | то же плюс постоянные ветки под окружения |

**При `env-branches` обязательно уточнить имена веток и что каждая означает** (`develop`→тест + `main`→прод · `staging`+`production` · свои). Угадывать нельзя.

**Человек назвал своё** («у нас Git Flow», «у нас свой процесс») → зафиксировать как есть. Уточнить три вещи: какие ветки постоянные, откуда ответвляются задачи, куда идут срочные правки. Не переучивать.

**Репозиторий публичный или упомянуты внешние участники** → добавить в `git-workflow.md` раздел про вклад из чужой копии репозитория. Отдельным вопросом не спрашивается.

## Шаг 3 — настройки интеграции

Показать **одним экраном с проставленными значениями**: «вот как это будет выглядеть — что поправить?». На входе B значения берутся из репозитория, иначе — из таблицы.

При `trunk` показывать нечего, кроме формата сообщений коммита: веток нет, вливать нечего. Экран сводится к одной строке, отдельного раздела в регламенте не появляется.

| Настройка | `trunk` | `branch-per-task` | `env-branches` |
|---|---|---|---|
| Как попадает в общую ветку | прямой коммит | схлопнуть в один коммит | схлопнуть в один коммит |
| Ветка после вливания | — | удалить | удалить, кроме веток окружений |
| Как догоняет общую | — | перенести коммиты поверх свежей | перенести поверх |
| Имена веток | — | `42-описание` при наличии задач, иначе `описание` | то же |
| Формат сообщений коммита | `тип: глагол` — тексты вариантов в `reference/commits.md` | то же | то же |
| Язык коммитов | русский; публичный репозиторий → предложить английский | то же | то же |
| Запрет прямой записи в общую ветку | нет | включить, если доступно | обязателен для прод-ветки |

Что человек поправил — то и попадает в доки. Убрал схлопывание — из шпаргалки уходят и упоминание схлопывания, и `git branch -D`.

## Шаг 4 — оси

Пять независимых решений, любая комбинация допустима. Тексты — `reference/axes.md`.

| Ось | Варианты |
|---|---|
| Ревью | `none` · `self-check` · `ship-show-ask` · `required` |
| Задачи | `none` · `hosting` (issues) · `external` (свой трекер) |
| Тесты | `deferred` · `critical` · `strict` |
| Проверка | `none` · `manual` · `ci` |
| Прод и выкат | `none` · `manual` · `gated` (готовит автоматика, нажимает человек) · `auto` |

Дополнения:

- **`review ≠ none`** → спросить **кто нажимает вливание**: автор после согласия · тот, кто согласовал · автовливание платформы · ИИ-агент (`reference/review-process.md`). Остальные строки регламента просмотра показать готовыми, на экране настроек. При выборе агента положить в регламент список того, что агент не вливает сам, и предложить поправить.
- **`ship-show-ask`** → положить в `git-workflow.md` критерии, что чем считается (`reference/axes.md`), и предложить поправить. Без критериев правило вырождается.
- **`tasks ≠ none`** → уточнить правило старта: «нет задачи — нет работы (кроме тривиальных docs/chore)» либо «крупное начинается с задачи».
- **`tasks=external`** → в доки идёт только ссылка на систему и имя переменной с ключом.
- **Состав проверки** не спрашивается: есть код — собрать из конфигов; стек выбран, кода нет — предложить обычный набор под стек и спросить, что убрать; стека нет — список по смыслу в конвенции.
- **Форма набора тестов, порог покрытия, стратегия выката** на бутстрапе не выбираются — дома по триггерам.

## Шаг 5 — проверить комбинацию

Перед генерацией. Предупреждение — **один раз**, человеческим языком, с конкретной рекомендацией. Человек настоял → зафиксировать как выбрано и добавить строку на пересмотр в триггеры.

| Условие | Что сказать |
|---|---|
| `prod=auto` + `tests=deferred` | Каждое вливание едет к пользователям, и ничто не проверяет, что оно не сломано. Минимум — тесты на критичное. |
| `prod=auto` + `check=none` | Между «влил» и «у пользователей» нет ни одной проверки. |
| `prod=gated` + `check ≠ ci` | Нажимать нечего: вариант предполагает, что автоматика готовит выкат. Либо проверка автоматическая, либо выкат руками. |
| `prod=auto` без описанного отката | Раздел отката в `runbooks.md` обязателен: что нажать и за сколько. |
| `prod=auto` + `strategy=trunk` | Незаконченное поедет к пользователям. Работает только с выключателями в коде. |
| Есть миграции + `prod ≠ none` | Напомнить правило разделения миграций. Разрушающая миграция одинаково необратима при любом способе выката — ручной лишь даёт время заметить. |
| `strategy=trunk` + `check=none` | Работа сразу в общей ветке держится на автоматической проверке. Без неё сломанное состояние видят все и сразу, а поймать его негде. Минимум — команда проверки, запускаемая перед `push`. |
| `check=ci` + кода ещё нет | Файл настроек проверок не создаётся — класть в него нечего. Правило «вливаем только с пройденной проверкой» уже записано, поэтому строка «появился первый код → создать настройки проверок» обязана быть в триггерах. Уведомление, не ошибка. |
| Вливает агент + `prod=auto` | Сказать прямо: агент не просто вливает, он выкатывает к пользователям — человека в цепочке до прода не остаётся. Убедиться, что список исключений заполнен и что откат описан. |
| Вливает агент + `check=none` | Агенту нечем проверить, что вливать можно: автоматических проверок нет, а согласие — не проверка кода. Минимум — команда проверки, которую агент запускает перед вливанием. |
| `review ∈ {ship-show-ask, required}` + `strategy=trunk` | Смотреть нечего — изменения попадают в общую ветку напрямую. Переспросить обе. |
| `strategy=trunk` + участников > 1 | Двое в одной ветке перетирают друг друга. |
| `tasks=none` + участников > 1 | Договорённости остаются в головах и расходятся. |
| `strategy=env-branches` + `prod=none` | Ветки под окружения без окружений. |
| `check=ci` + место репозитория неизвестно | Настройки проверок класть некуда — строка в триггеры. Уведомление, не ошибка. |

## Шаг 6 — генерация

**Ядро — всегда:** `AGENTS.md`, `CLAUDE.md`, `README.md` (существующий дополнить), `docs/README.md`, `docs/product.md`, `docs/decisions/{template.md,0001-vedyom-adr.md}`, `docs/workflow/{git-workflow.md,conventions.md,agents.md}`.

**По ответам:**

| Файл | Условие |
|---|---|
| `docs/workflow/project-workflow.md` | `tasks ≠ none` |
| шаблон предложения изменений | `strategy ≠ trunk` И место известно · GitHub: `.github/pull_request_template.md` · GitLab: `.gitlab/merge_request_templates/Default.md` |
| настройки проверок (`.github/workflows/tests.yml` / `.gitlab-ci.yml`) | `check=ci` И есть код И место известно |
| `docs/workflow/environments.md` | `prod ≠ none` |
| `docs/workflow/runbooks.md` | `prod ≠ none`; обязательные разделы — выкат, откат, резервная копия и восстановление |
| `docs/architecture/overview.md` | вход B либо архитектура выбрана |
| `docs/architecture/data-model.md` | то же И есть хранилище |
| `docs/decisions/0002-*` | состоялся осознанный выбор либо оформление принятого задним числом |
| `env.example` | в коде есть обращения к переменным окружения либо человек их назвал. Просто «есть код» — недостаточно: получится пустышка |

Несгенерированное → строка в «Дома по триггеру» в `docs/README.md`.

**Три состояния, а не два.** Скил различает не только «файл создан» и «файла нет»:

| Состояние | Что делать |
|---|---|
| Содержание есть | создать файл и заполнить |
| Содержания нет, дома тоже нет | строка в «Дома по триггеру»: «появится X → создать Y» |
| **Дом есть, а секция в нём пустая** | видимая пометка **внутри файла**: «пока не зафиксировано; появится — записывать сюда». Строку в триггеры **не** добавлять: она указывала бы на существующий файл, а самопроверка это ловит |

Третье состояние — норма, а не недоделка: сценарии, правила предметной области, источник схемы, стратегия выката появляются позже самих файлов. Пометка обязана быть видимой человеку — комментарий в разметке не считается, его не видно.

**Правила заполнения:**

- `{{...}}` → ответы интервью. После генерации `git grep -F '{{' -- '*.md'` возвращает пусто.
- `git-workflow.md`, `conventions.md` и правила в `AGENTS.md` собираются из фрагментов `templates/fragments/` — список блоков и условия в `templates/fragments/README.md`.
- **Ни одного упоминания отключённого процесса.** Нет задач — нигде «упомяни задачу»; нет проверки — нигде «зелёный CI»; нет ревью — нигде «апрув».
- Место репозитория GitLab → «merge request» всюду, GitLab-вариант защиты ветки; GitHub — наоборот. Место неизвестно → нейтральные формулировки.
- Язык — русский. Секретов в доках нет. `AGENTS.md` не раздувать: тест строки — «уберу, агент начнёт ошибаться? Нет → режу».

## Шаг 7 — гигиена, проверка, финал

1. `.gitignore` дописать: `logs/`, `scratch/*`, `!scratch/.gitkeep`, `CLAUDE.local.md`, `.env`. Создать `scratch/.gitkeep`.
2. **Самопроверка** по `reference/self-check.md` — обязательный шаг, не пропускать.
3. Отчёт: список файлов + принятые решения (архитектура, стратегия, настройки интеграции, пять осей, сработавшие предупреждения).
4. Первый коммит: `docs: разворачивает каркас документации проекта`. В пустом репозитории — прямо в общую ветку; для строгих стратегий это единственное допустимое исключение, дальше действует регламент.
5. **Репозиторий на хостинге**, если договорились создать: спросить и показать на подтверждение имя, владельца и приватность, затем `gh repo create <имя> --private --source=. --remote=origin --push` (GitLab — `glab repo create`, флаги сверить с `--help`).
6. Следующие шаги вне репозитория — перечислить, самому не делать: защита главной ветки по разделу в `git-workflow.md`, ключ трекера в окружение.
