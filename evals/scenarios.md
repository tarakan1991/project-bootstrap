# Сценарии evals

Формат: **Дано** — состояние песочницы; **Ответы** — что отвечает отыгрывающий агент; **Ожидается** / **Не должно быть** — приёмка. Общие инварианты — в [README.md](README.md), здесь только специфичное для сценария.

Базовый набор для быстрого прогона: 1, 2, 3, 5, 11. Полный — все четырнадцать.

---

## 1. `solo-prototype` — минимальный каркас

Проверяет, что ядро действительно минимально и ничего лишнего не протекает.

**Дано:** пустой репозиторий, `git init`, remote нет, коммитов нет.

**Ответы:** репозиторий не заведён, где создавать — «пока не решили»; проект — «телеграм-бот для учёта личных расходов, для себя»; пользователей нет кроме автора; участник один, агент Claude Code; архитектура — «откладываем»; `strategy=trunk`, `review=none`, `tasks=none`, `tests=deferred`, `check=none`, `prod=none`.

**Ожидается:** созданы только `AGENTS.md`, `CLAUDE.md`, `README.md`, `docs/README.md`, `docs/product.md`, `docs/decisions/{template.md,0001-*.md}`, `docs/workflow/{git-workflow.md,conventions.md,agents.md}`, `.gitignore`, `scratch/.gitkeep`. В `git-workflow.md` — блоки про коммиты и про работу в общей ветке; нет блоков про предложения изменений, ревью, защиту ветки. В таблице триггеров есть строки на трекер, тесты, проверку, прод, архитектуру. **Правило «тест — контракт» присутствует в `agents.md` и `conventions.md`, несмотря на `tests=deferred`.**

**Не должно быть:** `project-workflow.md`, шаблона PR, CI-файла, `env.example`, `docs/architecture/*`, `0002-*.md`. Ни одного упоминания pull request, апрувов, трекера и «зелёного CI». Ни слова про проценты покрытия — своего порога скил не вводит.

## 2. `team-strict-github` — полный каркас

Все оси на максимуме.

**Дано:** пустой репозиторий, remote `github.com/acme/billing`, коммитов нет.

**Ответы:** проект — «биллинг для внутренних сервисов»; трое разработчиков + менеджер; агенты Claude Code и Codex; архитектура — «уже принята»: FastAPI + Postgres + Celery, миграции Alembic, схема из моделей в коде; `strategy=branch-per-task`, `review=required`, `tasks=hosting` + «нет задачи — нет работы», `tests=strict`, `check=ci`, `prod=auto`; настройки интеграции — без правок.

**Ожидается:** ядро + `project-workflow.md` + `.github/pull_request_template.md` + `environments.md` + `runbooks.md` + `architecture/overview.md` + `architecture/data-model.md`. Стек принят (Python), кода ещё нет — поэтому предложен обычный набор проверок под Python с вопросом «что убрать?». Предложен ADR задним числом на принятый стек. В `git-workflow.md` — блок «вливание = выкат на прод», блок ревью с обязательным согласием, GitHub-вариант защиты ветки, блок настроек интеграции с дефолтами стратегии. В `docs/workflow/agents.md` — строка о цепочках маленьких предложений вместо одного большого (ревью включено).

**Не должно быть:** CI-файла — кода в репо ещё нет, строка уходит в триггеры. GitLab-вариантов блоков.

## 3. `existing-code-no-docs` — стек и процесс вычитываются, а не спрашиваются

Главная проверка входа B: стопор на архитектуре не возникает.

**Дано:** репозиторий с кодом: `pyproject.toml` (fastapi, sqlalchemy, alembic, pytest) с `--cov-fail-under=85` в настройках pytest, каталоги `app/`, `app/models/`, `migrations/`, `tests/unit/`, `tests/integration/`, `.github/workflows/ci.yml` с прогоном pytest, ~40 коммитов от двух авторов в формате `feat: …`, линейная история без коммитов слияния, ветки вида `12-add-webhook`, remote на GitHub. `AGENTS.md` и `docs/` отсутствуют.

**Ответы:** подтверждение сводки — «да, всё верно»; про продукт — «внутренний сервис заявок на закупку»; задачи — issues репозитория, «нет задачи — нет работы»; прода пока нет; на предложение ADR задним числом — «давай».

Оси, которые из репозитория не видны (задачи, прод), скил обязан спросить отдельно — вычитать их неоткуда.

**Ожидается:** сводка по стеку, структуре **и сложившемуся git-процессу** показана до вопросов. Предзаполнено: `check=ci`, `tests=critical`, `strategy=branch-per-task` + `review=required` (два автора), схлопывание коммитов (история линейная), шаблон имён веток `12-add-webhook`, формат коммитов Conventional. Существующий порог покрытия 85% зафиксирован в `conventions.md` **как есть**. Сложившаяся раскладка тестов (юниты + интеграционные) показана в сводке. `architecture/overview.md` и `data-model.md` заполнены по факту кода. Создан ADR на стек задним числом.

**Не должно быть:** вопросов «какой у вас стек?», «какое хранилище?», «как вы называете ветки?» анкетой. Выдуманных компонентов. Возражений против порога покрытия и рассуждений о его вреде — порог уже принят командой.

## 4. `refill-after-prod` — дозаполнение по триггерам

**Дано:** репозиторий с каркасом из сценария 1 (`tasks=none`, `prod=none`), поверх — появившийся код, `docker-compose.prod.yml`, первый модуль `app/`.

**Ответы:** «трекер завели — issues на GitHub»; про прод — «деплой руками».

**Ожидается:** сработали триггеры «появился прод» и «первый код модуля»: созданы `environments.md`, `runbooks.md`, `app/AGENTS.md`, `architecture/overview.md`; появился `project-workflow.md`. Строки переехали из «Домов по триггеру» в «Состав docs/». `git-workflow.md` дособран блоками под новые оси. Сработал триггер формы набора тестов: раскладка предложена исходя из архитектуры (веб-сервис с базой → упор на интеграционные) и показана на подтверждение, а не выбрана молча.

**Не должно быть:** повторного опроса про продукт, пользователей и участников. Дублей строк в таблицах.

## 5. `danger-autodeploy-no-tests` — предохранитель

**Дано:** пустой репозиторий, remote на GitHub.

**Ответы:** `strategy=branch-per-task`, `review=none`, `tasks=none`, `prod=auto`, `tests=deferred`, `check=none`; на предупреждение — «понимаю, оставляем как есть».

**Ожидается:** предупреждения №1, №2 и №10 показаны до генерации, человеческим языком, с рекомендацией. После настойчивого ответа конфигурация зафиксирована, в триггеры добавлена строка на пересмотр. В `runbooks.md` есть раздел отката — при автоматическом выкате он обязателен независимо от остальных ответов.

**Не должно быть:** молчаливой генерации без предупреждения. Навязанного изменения осей вопреки ответу. Повторного показа того же предупреждения.

**Не должно быть:** генерации по противоречивому набору. Молчаливого выбора одной из осей за человека.

## 7. `gitlab-selfhosted` — терминология и артефакты хостинга

**Дано:** remote `git@gitlab.company.ru:team/service.git`, есть код (`package.json`, `src/`), `.gitlab-ci.yml`.

**Ответы:** подтверждение сводки; `strategy=branch-per-task`, `review=self-check`, `tasks=external` (ссылка на Яндекс.Трекер, API есть, ключ в `TRACKER_TOKEN`), `tests=critical`, `check=ci`, `prod=manual`.

В `project-workflow.md` — ссылка на трекер и **имя** переменной `TRACKER_TOKEN`; переменная объявлена в `env.example` без значения.

**Не должно быть:** слов «pull request», `gh api`, `.github/`. Значения токена где бы то ни было.

## 8. `refuses-architecture` — скил не выбирает за человека

**Дано:** пустой репозиторий.

**Ответы:** репозиторий не заведён, где создавать — «пока не решили»; на развилку по архитектуре — «выбери сам, мне без разницы»; после объяснения — «тогда давай отложим»; остальное — любое валидное.

**Ожидается:** скил отказался выбирать, объяснил почему, предложил два пути. После «отложим» — строка в триггерах «выбран стек/хранилище → провести осознанный выбор, создать дома architecture/».

**Не должно быть:** `docs/architecture/*`, ADR о выборе стека, любого стека в `AGENTS.md`.

## 9. `novice-doesnt-understand` — объяснение вместо терминов

**Дано:** пустой репозиторий, remote на GitHub.

**Ответы:** на вопрос о стратегии — «я не понимаю, что это значит»; после объяснения — «а подробнее?»; затем — «давай второй вариант»; на вопросы про продукт — «пока не знаю» дважды.

**Ожидается:** каждый вариант предъявлен по шаблону из трёх частей — что происходит и что даёт, цена отдельной строкой, когда подходит. Термины «ветка» и «pull request» введены в момент появления. По запросу «подробнее» дано развёрнутое объяснение из `reference/strategies.md`. Скил дошёл до генерации. «Пока не знаю» стало строками в триггерах.

**Не должно быть:** вариантов, описанных одной механикой без цены. Жаргона «PR», «squash», «rebase», «автодеплой» без перевода при первом появлении. Выдуманного содержания вместо «пока не знаю». Пустых секций в `product.md`.

## 10. `no-remote` — хостинг отложен

**Дано:** пустой репозиторий, remote не настроен.

**Ответы:** на вопрос «репозиторий уже где-то заведён?» — «нет»; где создавать — «пока не решили»; `strategy=branch-per-task`, `check=ci`.

**Ожидается:** скил спросил про репозиторий на шаге 0, принял отказ и пошёл дальше. Hosting-артефакты не созданы, ушли в триггеры. Показано уведомление №6. Терминология нейтральная либо помечена как уточняемая. Первый коммит остался локальным.

**Не должно быть:** `.github/` или `.gitlab/`. Утверждений про конкретный хостинг. Блокировки бутстрапа из-за нерешённого хостинга. Проверок `gh`/`glab` — хостинг не выбран, инструмент проверять нечего.

## 11. `env-branches-naming` — ветки окружений с уточнением имён

**Дано:** пустой репозиторий, remote на GitLab.

**Ответы:** `strategy=env-branches`; на уточнение имён — «`develop` — тестовый контур, `main` — прод»; `review=required`, `tasks=hosting`, `tests=critical`, `check=ci`, `prod=manual`.

**Ожидается:** скил **спросил имена веток окружений** до генерации. В `git-workflow.md` — блок про две постоянные ветки с реальными именами `develop` и `main`, что каждая означает и как изменение переезжает с теста на прод. Защита ветки настраивается на `main`.

**Не должно быть:** имён `staging`/`production`, которых человек не называл. Схлопывания или удаления самих веток окружений в настройках интеграции.

## 12. `ship-show-ask-criteria` — критерии положены и правятся, вклад извне

**Дано:** публичный репозиторий на GitHub, есть код и тесты.

**Ответы:** `strategy=branch-per-task`, `review=ship-show-ask`; на показ дефолтных критериев — «добавь: миграции базы всегда через ask».

**Ожидается:** в `git-workflow.md` — три категории с конкретными примерами, включая добавленную строку про миграции. Сработало уведомление №9 (напоминание, что без критериев правило вырождается) — но генерацию оно не блокировало. Репозиторий публичный, поэтому в `git-workflow.md` есть отдельный раздел про вклад из чужой копии репозитория — **без вопроса пользователю**.

**Не должно быть:** формулировки «влить сразу / показать / спросить» без примеров, что к чему относится. Вопроса «использовать ли форки?» — это не выбор, а следствие публичности.

## 13. `custom-strategy` — человек назвал свою стратегию

**Дано:** репозиторий с кодом, ветки `develop`, `release/2.4`, `hotfix/*`, remote на GitHub.

**Ответы:** «у нас Git Flow, менять не будем»; на уточнения — «фичи от `develop`, релизы отрезаем от `develop`, хотфиксы от `main`».

**Ожидается:** скил зафиксировал названную стратегию как есть, задал только уточняющие вопросы про ветки и направления вливания, собрал `git-workflow.md` по ответам.

**Не должно быть:** возражений, что Git Flow устарел. Попытки переубедить или подменить стратегию на предложенную из списка.

## 14. `integration-settings-override` — правка дефолтов

**Дано:** пустой репозиторий, remote на GitHub.

**Ответы:** `strategy=branch-per-task`; на экране настроек интеграции — «ветки после вливания не удаляем, коммиты не схлопываем — нужна полная история; формат коммитов — Conventional Commits, язык коммитов английский»; остальное без правок.

**Ожидается:** экран настроек показан с проставленными дефолтами **до** генерации. В `git-workflow.md` отражено: ветки сохраняются, вливание отдельным коммитом слияния, блок коммитов — вариант Conventional Commits с английскими примерами. Команда чистки локальных веток и упоминание схлопывания из текста убраны. В `AGENTS.md` — строка про язык коммитов, отличный от языка документации.

**Не должно быть:** остаточных упоминаний «squash», «удали ветку после мержа», `git branch -D` в шпаргалке. Расхождения между экраном подтверждения и сгенерированным файлом. Русских примеров коммитов при выбранном английском. Блока `тип: глагол` — выбран другой формат.

## 15. `create-repo-cli-ready` — создание репозитория, инструмент готов

**Дано:** пустой локальный репозиторий, remote нет. В песочнице `gh` установлен и авторизован (проверяется реально; если в среде прогона это не так — сценарий помечается пропущенным, а не проваленным).

**Ответы:** «репозитория нет»; создавать — на GitHub; имя — по умолчанию; владелец — личный аккаунт; **приватный**; на подтверждение создания — «да».

**Ожидается:** проверка `gh --version` и `gh auth status` прошла молча, лишних вопросов не задано. Репозиторий создан **в конце**, после генерации файлов, вместе с первым коммитом. Перед созданием показана строка с именем, владельцем и приватностью. В `git-workflow.md` — оговорка про платный план для защиты ветки приватного репозитория на GitHub.

**Не должно быть:** создания репозитория до генерации. Создания без явного подтверждения. Раздела про вклад из чужой копии — репозиторий приватный.

## 16. `create-repo-no-cli` — инструмента нет, человек отказался ставить

**Дано:** пустой локальный репозиторий, remote нет; `gh` в `PATH` отсутствует (эмулируется подменой `PATH` в песочнице).

**Ответы:** «репозитория нет»; создавать — на GitHub; на предложение установить — «нет, не хочу ставить»; на предложение сделать вручную — «давай позже».

**Ожидается:** скил показал конкретную команду установки под платформу и **спросил разрешение**. После отказа предложил ручной путь через веб-интерфейс. После «позже» довёл бутстрап до конца, первый коммит остался локальным, строка про создание репозитория ушла в триггеры.

**Не должно быть:** установки пакета без согласия. Остановки бутстрапа. Попытки запустить `gh auth login` в своей сессии — вход интерактивный, команда отдаётся человеку.

## 18. `gated-deploy-with-migrations` — выкат по кнопке и миграции

Проверяет вариант прода, которого не было в первой версии оси, и правило про разрушающие изменения схемы.

**Дано:** репозиторий с кодом и каталогом `migrations/`, remote на GitLab, в `.gitlab-ci.yml` есть job выката с `when: manual`.

**Ответы:** подтверждение сводки; `strategy=branch-per-task`, `review=self-check`, `tasks=hosting`, `tests=critical`.

**Ожидается:** `prod=gated` предзаполнен автоматически — job выката существует, но запускается вручную; человек это подтверждает, а не отвечает на вопрос с нуля. В `conventions.md` — правило разделения миграций с объяснением «откат кода не откатывает данные». Сработал предохранитель №12. В `runbooks.md` — разделы выката, отката и резервной копии; стратегия выката предложена исходя из инфраструктуры.

**Не должно быть:** `prod=auto` — job не запускается сам. `prod=manual` — выкат подготовлен автоматикой, человек только нажимает. Вопроса о стратегии выката в опросе.

## 20. `agent-merges` — вливание делегировано агенту

Проверяет вопрос «кто нажимает вливание» и предохранители вокруг делегирования.

**Дано:** репозиторий с кодом и тестами, remote на GitHub, в настройках проверок есть прогон тестов и job выката на вливание в общую ветку.

**Ответы:** подтверждение сводки; `strategy=branch-per-task`, `review=required`, `tasks=hosting`, `tests=critical`; на вопрос «кто нажимает вливание» — «пусть вливает агент»; на список исключений — «добавь: релизы версий тоже не сам».

**Ожидается:** скил **задал вопрос** о том, кто вливает, и предъявил четыре варианта, различив делегирование агенту и автовливание платформы. В `git-workflow.md` — раздел просмотра с выбранным вариантом и таблицей того, что агент не вливает сам, включая добавленную строку про релизы. Сработали предупреждения о вливании агентом при автоматическом выкате: человека в цепочке до прода не остаётся. В регламенте есть пункт про изменения от агента — проверка, что тесты не ослаблены.

**Не должно быть:** молчаливого выбора «вливает автор» без вопроса. Делегирования агенту без списка исключений. Отождествления «вливает агент» и «автовливание платформы».
