# Регламент: работа с ИИ-агентами

Проект разрабатывается людьми и ИИ-агентами параллельно. Claude Code читает `CLAUDE.md` → `@AGENTS.md`; другие агенты (Codex и т.п.) читают `AGENTS.md` напрямую. Контекст-файлы — это **бюджет инструкций**, а не документация: кладём только то, что агент не выведет из кода или одним поиском (подробнее — `docs/README.md`, принцип 6).

## AGENTS.md — живой документ

Модульный `AGENTS.md` обязан стареть медленнее кода. Это закрывается **триггерами** (когда обновлять) и **дисциплиной записи** (что писать).

### Триггеры — когда агент обязан обновить модульный AGENTS.md

Только эти случаи. «Прочитал и захотелось добавить» — НЕ триггер (это и есть петля «агент пишет себе доку для следующей сессии»).

1. **Файл отсутствует или пустой.** Агент, начинающий первую задачу в модуле, создаёт черновик по шаблону ниже — в том же PR, что и его основное изменение.
2. **Поймал грабли в этой сессии.** Что-то сломалось, потратил >10 минут на разбор, причину можно сформулировать одной строкой → дописать в «Грабли» в том же PR.
3. **Менял публичный контракт модуля.** Новая команда запуска, новый endpoint в карте, новый инвариант — обновить «Где что лежит» / «Конвенции» в том же PR.
4. **Меняется состав стека модуля.** Добавлен/удалён значимый пакет в манифесте зависимостей, новый внутренний модуль/каталог, новая интеграция (БД, очередь, внешний API) — отразить в карте/стеке. Тривиальные апдейты версий — НЕ триггер.

### Дисциплина записи

- **Тест на каждую строку:** «уберу — агент начнёт ошибаться? Нет → не пишу». Если строка выводится из `ls` или первых строк главного файла модуля — она не нужна.
- **Бюджет ≤80 строк** на модульный AGENTS.md. Исключения фиксируются явно (в самом файле — почему он больше).
- **Code-grounded:** перед записью — посмотрел в `<файл:строка>`, не «мне кажется». В commit message одна строка «почему» («увидел в conftest.py, что env ставится в каждом файле — добавил граблю»).
- **Один факт — один дом:** длинный нарратив про модуль и решения — в `docs/architecture/<модуль>.md` и ADR, а не в AGENTS.md. AGENTS.md — это «как работать здесь», не «как всё устроено».

### Что агенту НЕЛЬЗЯ править без явной задачи

- ADR в `docs/decisions/` (immutable — решение устарело → новый ADR со статусом `supersedes 00XX`)
- Корневой `AGENTS.md` и `CLAUDE.md` (контракт всей команды)
- Корневой `README.md`
- Reference-секции в `docs/architecture/*` про API/env/CLI-флаги — они должны генерироваться из кода (OpenAPI, `env.example`), не писаться руками

Модульный `AGENTS.md` править **можно**, но только по триггерам выше.

## Каскадное обновление — правило «один факт — один дом» на практике

Когда человек просит «добавь X в доки» или «актуализируй Y» — агент НЕ правит первый попавшийся файл и не закрывает задачу. Он **проверяет все места**, где этот факт может жить, и обновляет их в одном PR. Иначе в `docs/architecture/` останутся устаревшие данные, а в `AGENTS.md` — новые.

### Шаг 1 — перед правкой: поиск всех домов факта

```bash
git grep -i '<ключевое слово или имя сущности>' -- '*.md'
```

Например, переименование сущности — `git grep СтароеИмя -- '*.md'`; новая env-переменная — `git grep '<NAME>' -- '*.md' env.example`.

### Шаг 2 — пары, которые реально могут разойтись

Чек-лист перед PR — пробежать и убедиться, что ничто не противоречит (адаптировать под стек проекта):

| Правил в … | Проверь тоже |
|---|---|
| `docs/architecture/<m>.md` (архитектура модуля) | `<модуль>/AGENTS.md` — в карте/конвенциях не осталось старого |
| `<модуль>/AGENTS.md` (модульный) | `docs/architecture/<m>.md` — нарратив согласован |
| Корневой `AGENTS.md` (стек / глобальные правила / карта) | все затронутые модульные `AGENTS.md` |
| Новый ADR в `docs/decisions/` | `docs/architecture/*.md` отражают новое состояние; старый ADR получил `superseded by 00XX` |
| `docs/workflow/conventions.md` (общие конвенции) | модульные `AGENTS.md` не противоречат |
| `README.md` (видение/запуск/тесты) | `docs/README.md` — карта доков, состав `docs/` совпадает с реальным |
| `env.example` (новая env-переменная) | `docs/architecture/*.md` упоминает её в нужном модуле |
| Манифест сервисов (docker-compose и т.п.) | `docs/architecture/overview.md` имеет этот сервис; если у него есть свой каталог — есть и `AGENTS.md` (или пустой по триггеру №1) |

### Шаг 3 — обновить **всё** в одном PR

Если факт живёт в нескольких файлах — правятся все файлы в одном PR. Разбивать на два PR «сначала AGENTS.md, потом architecture» — НЕЛЬЗЯ: между мержами в main будет временное расхождение, которое второй PR может и не закрыть.

Связанный принцип в `docs/README.md`: «один факт — один дом». Каскадное обновление — практика, которая этот принцип поддерживает: если нашлись два дома одного факта — оставить источник, остальное заменить ссылкой.

## Шаблон для нового/пустого модульного AGENTS.md

Заполнять по порядку. Удалить TODO-комментарии. Пустые секции (например, «Грабли» в первый день жизни модуля) — оставлять с пометкой «пока пусто» или удалять; не выдумывать содержание.

```markdown
# <модуль> — <одна фраза о scope>

Запуск: <конкретная команда>
Тесты: <конкретная команда; если нет тестов — пропустить раздел>
<Миграции / lint / другие частые команды модуля, если есть>

## Где что лежит
- `<подпапка/>` — <что там, одной строкой>. <Ловушки, если есть>
- <...>

## Конвенции
- <Договорённость, которую агент НЕ выведет из кода>
- <...>

## Грабли
- <Конкретная боль из прошлой сессии, одной строкой: симптом → причина/правило>
- <...>

## Чего НЕ делать
- <Негативная инструкция, особенно про вещи, которые легко сломать «улучшением»>
- <...>

Глубже: `docs/architecture/<модуль>.md` · решения → `docs/decisions/`
```

### Чек-лист «что должно быть в Граблях»

Перед коммитом нового или обновлённого AGENTS.md — пробежаться по списку. Если что-то из этого живёт в модуле и **не зафиксировано** ни в коде явно, ни в AGENTS.md — оно станет следующей граблёй на следующей сессии.

- **Скрытые состояния:** кэши настроек, module-level singleton, глобальные переменные.
- **Сайд-эффекты dependency:** что коммитит сама, что коммитит её caller, что закрывается автоматически.
- **Тесты с особенностями:** in-memory БД, фикстуры, env-инициализация ДО импортов, запреты на параллельный запуск.
- **Сериализация / параллелизм:** mutex, очереди, инварианты типа «не запускать два процесса на одном ресурсе».
- **Контракты с другими сервисами:** форматы, заголовки, общие каталоги.
- **Среда:** обязательные env, которые модуль явно не использует, но падает без них.
- **Хитрая конфигурация драйверов/пакетов:** нестандартные строки подключения, PATH-манипуляции, прокси.
- **Тайм-зоны и сравнения дат** между разными хранилищами (naive vs aware).
- **Анти-фичи by design:** что НЕ настраивается специально (CORS, фолбэки, авто-ретраи).

Если строка из чек-листа не применима — пропустить. Если применима, но в коде уже выражена явным комментарием/исключением, который агент гарантированно увидит — тоже пропустить.
