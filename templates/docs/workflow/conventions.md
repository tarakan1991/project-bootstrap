# Конвенции разработки

> Договорённости по коду и инварианты проекта. Механика git (ветки, коммиты, PR) — в `git-workflow.md`.

## Что нельзя трогать без согласования

- **Секреты и их хранилища** (env, ключи, токены) — не коммитить, не переносить, не логировать.
- **Схема БД** — только через миграции{{ (инструмент из вопроса 5)}}; правка модели = миграция в том же PR.
- **Новые зависимости** — не добавлять пакеты без согласования с владельцем (одной строкой в задаче/PR: зачем и почему именно этот).
- **CI-конфиг** (`.github/workflows/`) — не менять мимоходом в feature-PR; изменение CI — отдельная задача.

## Тесты

<!-- ВАРИАНТ «строго»: -->

<!-- ВАРИАНТ «прагматично»: -->
**Политика: прагматично.** Тесты обязательны для критичной бизнес-логики (деньги, данные пользователей, необратимые операции); остальное — по усмотрению автора.
<!-- ВАРИАНТ «отложено»: -->

## Полная проверка перед PR

Единая команда «я закончил, проверяю всё» (тесты + линт + сборка):

```
TODO — появится с первым кодом; собрать в одну команду (make check / npm run check / скрипт)
```

Пока команды нет — этот блок и есть напоминание её завести.

## Деструктивные операции на проде

Перед любой операцией, которая может потерять данные, — **бэкап** задетых таблиц/файлов. «Я проверил, что таблица пустая» — недостаточно: запрос можно сформулировать с ошибкой, `WHERE` промахнуться, сервис в фоне успеет писать. Конкретные команды — в `runbooks.md` (дом появится с продом, см. таблицу триггеров).

## Логи и отладка

- **Логи** локальной разработки → `logs/` (в `.gitignore`), не в репозиторий. Путь в коде — относительно корня проекта: `logs/<service>.log`.
- **Временные и отладочные скрипты** → `scratch/` (в `.gitignore`, в репозитории только сама папка через `.gitkeep`). Не разбрасываем разовые скрипты и `*.log` по корню и модулям.
