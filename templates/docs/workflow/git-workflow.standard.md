# Рабочий процесс: git-репозиторий

> Механика работы с гитом: ветки, коммиты, PR, rebase. Режим «стандарт»: PR-only, самомерж автором по зелёному CI.
> Конвенции кода и инварианты («что нельзя трогать») → `conventions.md`. Управление задачами → `project-workflow.md`.

## ⚠️ Главное: что означает мерж в `main`

<!-- ВАРИАНТ A — мерж в main запускает автодеплой на прод. Оставить этот блок, удалить вариант B. -->
Мерж в `main` запускает автодеплой на прод. **Каждый мерж = выкат в продакшен.** Из этого следует всё остальное:

- мержим **только** зелёный CI;
- проверка результата после мержа происходит уже **на проде**;
- PR **не** закрывает задачу автоматически (без `Closes #N`) — закрываем вручную после проверки на проде.

<!-- ВАРИАНТ B — автодеплоя нет (или прода пока нет). Оставить этот блок, удалить вариант A. -->
`main` всегда в рабочем состоянии: собирается, проверка зелёная. Мержим только зелёный CI. Деплой — отдельное осознанное действие.

`main` — **домашняя база**. Между задачами ты стоишь на свежем `main`; рабочие ветки одноразовые и короткоживущие. Не «живёшь» на фиче-ветке неделями — иначе локальный `main` устаревает и возвращаться после мержа некуда (типичная грабля).

## Ветки

Формат `{номер-задачи}-описание`, например `42-добавить-регистрацию`. Номер берётся из задачи в трекере — «нет задачи — нет работы» (исключение — тривиальные `docs`/`chore`, см. «Быстрая правка не по теме»). Если трекер — GitHub, ветку удобно создавать кнопкой `Create a branch` на странице issue: она и привязывает ветку к задаче, и ответвляется от актуального `main`.

## Коммиты

Русский язык, формат `тип: глагол + что делает`. Типы: `feat`, `fix`, `chore`, `docs`, `refactor`. Без точки в конце, не длиннее 72 символов. Примеры:
```
feat: добавляет обработчик регистрации
fix: исправляет ошибку валидации API-ключа
docs: обновляет AGENTS.md после рефакторинга
```

## Жизненный цикл ветки

```bash
# СТАРТ — всегда от свежего main
git checkout main && git pull
git checkout -b 42-краткое-описание

# ... работаем, коммитим ...

# ПЕРЕД PR — подтянуть main под себя
git fetch origin && git rebase origin/main
# rebase переписал историю → обычный push отлетит, нужен force-with-lease
git push --force-with-lease origin 42-краткое-описание

# PR: base main, в описании упоминаем задачу
# CI зелёный → автор сам жмёт Merge (squash)
# удалённая ветка удаляется автоматически (настройка репо)

# ВЕРНУТЬСЯ ДОМОЙ — обязательный шаг, без него остаёшься на смерженной ветке
git checkout main && git pull          # подтянули собственный мерж
git branch -D 42-краткое-описание      # squash-мерж не виден как merge → нужен -D, не -d
```

## Приём PR (без взаимного код-ревью)

Код-ревью друг друга сейчас нет — фиксируем это честно, а не как костыль:

- **PR всё равно обязателен.** Он гоняет CI, даёт историю изменений и связь с задачей.
- **Мерж — самомерж автором** по зелёному CI. Перед кнопкой Merge — самопроверка по Definition of Done (`project-workflow.md`): полная проверка прогнана, критерий готовности выполнен, доки/ADR обновлены, если затронута архитектура. Чужих глаз нет — эта самопроверка их заменяет.
- **Метод мержа — squash** (репозиторий настроить на squash-only): один коммит на задачу, линейная история `main`.
- **Прямой push в `main` не используем** (только PR) — договорённость, даже если технически не заблокирован (см. «Защита ветки» в конце).

## Быстрая правка не по теме (cameo fix)

Понадобилось внести мелкую правку (доку, опечатку), пока сидишь в незаконченной фиче? **Не** коммить её в текущую фичу и **не** ответвляйся от фичи — иначе утащишь её несмёрженные коммиты в посторонний PR. Ответвляйся **от свежего `main`**:

```bash
git stash push -- путь/к/файлу        # если уже что-то наредактировал в фиче
git fetch origin
git checkout -b docs-краткое-описание origin/main
git stash pop
# правка → коммит → PR → squash-merge
git checkout 42-краткое-описание       # вернулись в свою фичу
```

Тривиальные `docs`/`chore` можно вести без отдельной задачи — это исключение из «нет задачи — нет работы».

## Откат

Сломавший мерж откатывается **тоже через PR** (с squash это быстро):

```bash
git checkout main && git pull
git checkout -b revert-<что-откатываем>
git revert <sha коммита-мержа>         # squash-мерж = один коммит, откатывается целиком
git push origin revert-<что-откатываем>
# PR → squash-merge
```

Не правь `main` напрямую даже в пожар. Единственное исключение — когда сломан сам CI и мерж невозможен: тогда чинит владелец/админ, осознанно и руками.

## Правила (шпаргалка)

- Старт ветки — всегда от свежего `main`; между задачами стоишь на `main`.
- Перед PR — `git rebase origin/main`. Пуш rebase-нутой ветки — только `--force-with-lease`, **никогда** `--force`.
- Длинные ветки (живут >1–2 дней) периодически ребейзим; обязательно — перед PR.
- `merge` между ветками руками не используем — только `rebase`.
- <!-- ВАРИАНТ A: -->PR упоминает задачу, но БЕЗ `Closes #N` — мерж не должен закрывать её до проверки на проде; закрываем вручную.<!-- ВАРИАНТ B: -->PR упоминает задачу; автозакрытие (`Closes #N`) допустимо, если проверка происходит до мержа.
- Метод мержа — **squash**. Удалённая ветка удаляется автоматически; локальную чистим `git branch -D`.
- Залежи локальных веток: `git fetch --prune`, затем удалить помеченные `[gone]`.
- Прямой push в `main` — не используем (PR-only), даже если технически открыт.
- Тривиальные `docs`/`chore` — можно без задачи; всё остальное — задача обязательна.
- Времянки → `scratch/`, логи → `logs/` (см. `conventions.md`).
- Перед PR — полная проверка одной командой (`conventions.md`); docs-only изменения CI не гоняют.

## Защита ветки + auto-merge

<!-- ВАРИАНТ GitHub — оставить этот блок, удалить блок GitLab ниже. -->
Branch ruleset для приватного репо требует платного плана GitHub (для публичного доступен на free). Пока недоступно — держимся на дисциплине; когда доступно, включает владелец/админ:

**1. Repo settings — auto-merge и авто-удаление веток:**
```bash
gh api -X PATCH repos/{{OWNER}}/{{REPO}} -F allow_auto_merge=true -F delete_branch_on_merge=true
```

**2. Ruleset на `main` — PR обязателен, зелёный CI обязателен, 0 апрувов:**
```bash
gh api -X POST repos/{{OWNER}}/{{REPO}}/rulesets --input - <<'EOF'
{
  "name": "main protection",
  "target": "branch",
  "enforcement": "active",
  "conditions": { "ref_name": { "include": ["~DEFAULT_BRANCH"], "exclude": [] } },
  "rules": [
    { "type": "pull_request",
      "parameters": {
        "required_approving_review_count": 0,
        "dismiss_stale_reviews_on_push": false,
        "require_code_owner_review": false,
        "require_last_push_approval": false,
        "required_review_thread_resolution": false
      }
    },
    { "type": "required_status_checks",
      "parameters": {
        "strict_required_status_checks_policy": false,
        "required_status_checks": [
          { "context": "TODO-имя-CI-check" }
        ]
      }
    },
    { "type": "non_fast_forward" }
  ]
}
EOF
```

> Нюанс docs-only: CI-workflow стоит на `paths-ignore` для `*.md`/`docs/**`, поэтому required-check в docs-only PR останется в состоянии pending и заблокирует мерж. Решение — job-пустышка с тем же именем check'а на docs-only путях (`paths: ['**/*.md', 'docs/**']`), которая сразу завершается успехом.

**3. На каждом PR** нажимать «Enable auto-merge (squash)» — PR вольётся сам, как только CI позеленеет. Прямой push в `main` после этого физически закрыт.

После включения обновить этот раздел и «Приём PR»: договорённость «PR-only» → техническое enforcement.

<!-- ВАРИАНТ GitLab — оставить этот блок, удалить блок GitHub выше. -->
Protected branches в GitLab бесплатны (включая self-hosted CE) — включаем сразу, выполняет владелец/админ:

1. **Settings → Merge requests:** «Squash commits when merging» = **Require** (один коммит на задачу, линейная история); «Pipelines must succeed» = on; «Skipped pipelines are considered successful» = on — иначе docs-only MR (пайплайн по правилу не запускается) не сможет влиться.
2. **Settings → Repository → Protected branches:** `main` — Allowed to push and merge: **No one** (push) / **Maintainers** или Developers + Maintainers (merge). Прямой push в `main` закрыт физически.
3. На каждом MR — **«Merge when pipeline succeeds»**: MR вольётся сам по зелёному пайплайну.
4. Обязательные апрувы (Merge request approvals) — платная фича (Premium). На Free/CE самомерж по зелёному пайплайну + самопроверка по DoD — как описано в «Приёме PR».
